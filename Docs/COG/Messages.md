# COG Messages

This page documents the message ids registered by `sithCog_Initialize()` and the runtime rules that affect how handlers receive them.

## Message Context Accessors

The system verbs below expose the current message context:

| Verb | Meaning |
| --- | --- |
| [`GetSenderType()`](Functions-System.md#getsendertype) | Sender reference type, for example thing, surface, sector, or cog. |
| [`GetSenderRef()`](Functions-System.md#getsenderref) | Sender reference/index. |
| [`GetSenderID()`](Functions-System.md#getsenderid) | Sender link id. For linked dispatch this is the `linkid` from the symbol ref. |
| [`GetSourceType()`](Functions-System.md#getsourcetype) | Secondary source type, if one was supplied. |
| [`GetSourceRef()`](Functions-System.md#getsourceref) | Secondary source reference/index. |
| [`GetParam(i)`](Functions-System.md#getparam) | Current integer message param `0` through `3`. |
| [`SetParam(i, value)`](Functions-System.md#setparam) | Overwrite the current cog's param slot. |
| [`ReturnEx(value)`](Functions-System.md#returnex) | Set the handler return value. Important for messages such as `damaged`. |

## Registered Message Names

OpenJones3D registers 47 numeric message ids plus one extra alias:

- `activate`
- `activated` (alias of `activate`)

## Known Engine-Supplied Payload Conventions

Not every engine-generated message uses the [`GetParam()`](Functions-System.md#getparam) slots. Many messages rely mostly on sender/source/link context instead. The rows below only list payloads that are explicitly populated by the current engine code.

| Message | Payload | Notes |
| --- | --- | --- |
| `aim` | [`GetParam(0)`](Functions-System.md#getparam): `1` = aiming, `0` = not aiming | Sent to the current weapon/item cog. The source thing is the actor/player doing the aiming. |
| `timer` | [`GetSenderID()`](Functions-System.md#getsenderid): timer id for [`SetTimerEx()`](Functions-System.md#settimerex); [`GetParam(0..1)`](Functions-System.md#getparam): custom ints from [`SetTimerEx()`](Functions-System.md#settimerex) | Plain [`SetTimer()`](Functions-System.md#settimer) does not supply custom params. |
| `damaged` | [`GetParam(0)`](Functions-System.md#getparam): incoming damage amount; [`GetParam(1)`](Functions-System.md#getparam): damage type | Source is the damaging thing when available. |
| `killed` | [`GetParam(1)`](Functions-System.md#getparam): damage type | The current kill path leaves [`GetParam(0)`](Functions-System.md#getparam) at `0`. Source is the killing thing when available. |
| `missed` | [`GetParam(0)`](Functions-System.md#getparam): projectile damage; [`GetParam(1)`](Functions-System.md#getparam): damage type | Sent from the shooter thing when a projectile misses. |
| `aievent` | [`GetParam(0)`](Functions-System.md#getparam): AI event id; [`GetParam(1)`](Functions-System.md#getparam): current AI mode; [`GetParam(2)`](Functions-System.md#getparam): caller-specific payload | The exact meaning of [`GetParam(2)`](Functions-System.md#getparam) depends on the event subtype and the object passed by the AI caller. |
| `statechange` | [`GetParam(0)`](Functions-System.md#getparam): state-change type; [`GetParam(1)`](Functions-System.md#getparam): state-specific payload | Current AI sends use armed mode for armed-mode changes and move flags for anim-move changes. |
| `callback` | Usually [`GetParam(0)`](Functions-System.md#getparam): puppet track number; [`GetParam(1)`](Functions-System.md#getparam): key-marker type | Some ad-hoc sends only populate [`GetParam(1)`](Functions-System.md#getparam) with a marker constant and leave [`GetParam(0)`](Functions-System.md#getparam) as `0`. |
| `trigger` | [`GetParam(0..3)`](Functions-System.md#getparam): forwarded exactly from [`SendTrigger(...)`](Functions-System.md#sendtrigger) | Sender is the local player thing in the current helper implementation. |
| `fire` | No universal payload. Some puppet attack callbacks send `GetParam(0) = -1` | Many other engine fire sends are paramless, so scripts should also inspect sender/source context. |

Messages that usually carry their context outside the param array include:

- `selected` and `deselected`, which often encode the item/weapon type through sender context such as `GetSenderType() == int` and `GetSenderRef() == typeId`
- `changed`, which is reused by multiple systems and can carry meaning through sender/source/link fields instead of fixed params
- `taken`, `respawn`, `entered`, `exited`, `crossed`, `touched`, `boarded`, `unboarded`, and `newplayer`, which currently have no fixed universal [`GetParam()`](Functions-System.md#getparam) payload in the engine send sites

## Important Runtime Behavior

### `loading`

Each cog receives `loading` after its symbol references have been parsed during `sithCog_Open()`. This is earlier than the global `startup` broadcast.

### `startup`

`startup` is broadcast during the level-open post-process path after time and player inventory are reset.

### `shutdown`

`shutdown` is broadcast during cog-system close before cogs are freed.

### `pulse`

`pulse` is generated by [`SetPulse(seconds)`](Functions-System.md#setpulse). The cog keeps receiving it until the pulse is cleared or disabled.

### `timer`

`timer` can come from three different places:

- [`SetTimer(seconds)`](Functions-System.md#settimer) on the cog itself
- [`SetTimerEx(...)`](Functions-System.md#settimerex) through the event queue
- thing helpers such as [`SetThingTimer()`](Functions-Thing.md#setthingtimer)

For [`SetTimerEx()`](Functions-System.md#settimerex), the first extra integer becomes the timer id that later shows up through [`GetSenderID()`](Functions-System.md#getsenderid). The remaining two integers become message params `0` and `1`. Params `2` and `3` are zero in the current implementation.

### `damaged`

`damaged` is special:

- thing, sector, and surface dispatch paths treat the incoming damage amount as the initial return value
- each handler can override that value with [`ReturnEx()`](Functions-System.md#returnex)
- when multiple thing-linked handlers run, the updated damage is propagated to the next handler in the chain

That makes `damaged` the main hook for script-side damage filtering or modification.

## Dispatch Order And Link Filtering

For thing messages, the current engine dispatch order is:

1. the thing's own cog
2. the thing's capture cog
3. every cog linked to that thing through `symbols` refs

For sector and surface messages, only the linked-cog lists are used.

Two practical consequences follow from that:

- [`GetSenderID()`](Functions-System.md#getsenderid) is the configured `linkid` only for the linked-dispatch leg
- linked sector/surface/thing sends honor the symbol ref's `mask`, so a source thing whose type does not match the mask will not trigger that linked handler
- when there is no concrete source thing, the engine tests the link against `SITH_THING_FREE`, which is why the parser's default link mask includes that bit alongside `SITH_THING_PLAYER`

<a id="created-initialized-devmode-caveat"></a>

### `created` And `initialized`

There are two important delivery paths:

- During normal level open, `sithOpenPostProcess()` walks existing thing cogs and sends both messages.
- During ad-hoc thing creation/initialization, the runtime only sends them when [`SITHDEBUG_INEDITOR`](Flags.md#debug-mode-flags) is not set.

So if you are testing under devmode/editor mode, freshly spawned things may skip their automatic `created` and `initialized` handlers even though the initial level-open pass still delivers them.

### `user0`

`user0` is heavily reused by the game. Examples in the current tree include:

- savegame/master-cog notifications
- item pickup flows
- whip interactions
- some player-control paths

When restoring a savegame while [`SITHDEBUG_INEDITOR`](Flags.md#debug-mode-flags) is active, the master-cog `user0` restore notification is intentionally skipped.

### `user2` And `user3`

`JonesCog` sends:

- `user2` to the local player thing cog when a cutscene begins
- `user3` to the local player thing cog when a cutscene ends

If your project-specific cogs depend on Jones cutscene state, those two hooks are worth checking.

## Linked Sender Semantics

When a message is delivered through a `thing`, `sector`, or `surface` symbol ref with `linkid`:

- [`GetSenderType()`](Functions-System.md#getsendertype) returns the linked sender type
- [`GetSenderRef()`](Functions-System.md#getsenderref) returns the linked sender reference
- [`GetSenderID()`](Functions-System.md#getsenderid) returns the configured `linkid`

That is why [`GetSenderID()`](Functions-System.md#getsenderid) should be read as "link id" rather than "thing id".

## Multiplayer Caveat

In multiplayer, non-`startup` and non-`shutdown` messages sent to non-local cogs are generally forwarded through the network layer unless the cog is marked local. `pulse` and `timer` are not forwarded in that same way.
