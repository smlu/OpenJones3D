# Synthetic SmushPlay lifecycle fixtures

These fixtures and expected pixels are authored test data. They contain no game
assets and were not captured from or generated by an original executable. They
exercise the reconstructed player with its actual file, stream and raw Bl16
decoder implementations.

Run `python generate.py` in this directory to regenerate the files, or
`python generate.py --check` to verify them without writing. The generator uses
only Python's standard library. `metadata.json` records dimensions, callback
order, serialized values and SHA-256 hashes.

| File | Purpose |
| --- | --- |
| `SANM.snm` | Plain SANM under a registered movie extension; its final four bytes are zero. |
| `SANM.san` | Identical plain content under an unregistered extension. |
| `ZNM.znm` | Gzip of exactly the same SANM bytes under the other registered extension. |
| `expected-rgb565.bin` | Three complete row-major 8x8 RGB565 images, little-endian, 128 bytes each. |

The three frames are specified independently of any decoder:

1. An eight-color diagonal pattern. At `(x,y)`, select color `(x+y) mod 8` from
   red, green, blue, white, black, yellow, magenta and cyan in RGB565.
2. A coordinate pattern with five-bit red `(3x+5y+1) mod 32`, six-bit green
   `(7x+3y+2) mod 64` and five-bit blue `(5x+7y+3) mod 32`.
3. All zero pixels. This also makes the plain movie end in four zero bytes,
   reproducing the input property behind the gzip-transparency startup hang.

One complete play must produce four callbacks with frame indexes `0,1,2,3` and
128 matching pixel bytes per callback. Their image indexes are `0,1,2,2`: the
END state in `Framestream.c` retains the final chunk, increments the frame index
and presents that final image once more before returning `ANIMPLAY_STATE_END`.
Two loops repeat this four-callback sequence. The SHDR count remains **3**,
matching the three distinct FRME chunks; success must not rely on a later
malformed-header/error exit. The first two nonzero, distinct images prevent
blank callbacks from satisfying the golden. This terminal callback convention
was checked against both the reconstructed source and native lifecycle playback.

All frames use raw Bl16 codec 0 and bitmap type 3 (RGB565), not a pixel bit count
in that type field. Serialized `FrameHeader` and `Bl16Header` layouts retain
their complete 0x416-byte and 0x230-byte headers, so the plain file is 3,198
bytes. The gzip header has no filename, a zero timestamp and OS byte 255.
Regeneration uses compression level 9; compressed output may differ if a future
Python/zlib version changes its deflate encoding, in which case validate the
uncompressed content and update the recorded compressed hash deliberately.

The clip contains no audio packets. Lifecycle tests may use a fake DirectSound
device, but these goldens make no assertion about audible output, synchronization
or a real display device. Existing retail-vector fixtures are separate.
